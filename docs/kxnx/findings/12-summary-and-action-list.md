### 关于线简化：我们和奎享是两条不同路线（findings/13）

`PathParameters.simplePaths = 0.02f` —— 奎享的简化容差是 **0.02mm**，我们是 **0.1mm**，差 5 倍。
这不是"我们设错了"，而是两种消除卡顿的思路：

| | 奎享 | hutuji 现状 |
|---|------|------------|
| 保精度 | ✅ 0.02mm 几乎不简化 | ⚠️ 0.1mm 轻度简化 |
| 消卡顿靠什么 | 窗口化流控吸收往返 | 降低行数减少往返次数 |
| 小字/密集细节 | 好 | 可能显棱角 |
| 实现复杂度 | 高（双队列+字节计数） | 低（一个参数） |

**当前选择保留 0.1mm**——它已实测把卡顿消掉（实机串口 92 行全在 6ms 收 ok、0 行阻塞、整图 6.3s），成本一个参数。
但要知道代价：这是**以画面精度换流畅**。若将来出现"小字不好看"的反馈，正解不是继续调容差，
而是做 P2 的窗口化流控，然后把容差降回 0.05mm 甚至 0.02mm。

## 三、落地清单（按优先级）

### P0：让笔能落纸 —— 🟡 会话基准代码对齐中，待烧录验证

#### 动作 1：下载文件模板已对齐；补齐会话旁路基准

依据是 kdraw 缓存的 `2..10.gcode`；9 个文件 SHA256 完全相同，只算 **1 个唯一产物的 9 个副本**，
并非 9 份独立样本。下载文件模板保持：

```toml
document_start = "G21\nG90\nF8000\nG1G90 Z0.0F10000\nG1G90 Z0.0F10000\n"
segment_first  = "G0 X{x:.3f}Y{y:.3f}F8000\nG1G90 Z5.0F10000\n"
segment        = "G1 X{x:.3f}Y{y:.3f}F8000\n"
line_end       = "G1G90 Z0.0F10000\n"
document_end   = "G1G90 Z0.0F10000\n"
```

- 下载文件使用 Z5 落笔、Z0 抬笔，全文 0 个 M 码和 0 个 G92；校验器继续拒绝 G92
- 开头两次 `G1 Z0` 只是缓存兼容的幂等运动，不能建立坐标基准
- 完整会话每次首画/重画前须 fresh `Idle` + 100ms，再由 S3 旁路固定 `G92 Z0`
- 收尾**不照抄**奎享的 `G90G0 X0Y0`（本机固件判为换纸触发，§5 禁止）
- 证据：findings/01, 02, 05, 06, 07 + 真实产物与反编译会话路径
- 2026-07-27 COM3 只证明 Grbl 计数到 Z5/Z0；新编排的短线真实出墨待烧录验证

#### 动作 2：保持奎享本机 `$1=25`、`$3=7`

奎享本机 `Grbl.json` 明确包含 `$1=25`、`$3=7`。`$1=25` 后电机失能，弹簧回到自然抬笔位，
但 Grbl 计数不会跟随机械回弹；因此必须等待超过 25ms 后旁路 `G92 Z0`，不能靠两次普通 Z0
建立基准。S3 采用 100ms，且不改 `$1/$3`。

### P2：性能 + 恢复精度（部分已提前完成）

当前用 `linesimplify` 换流畅。奎享保 0.02mm 精度还能流畅，靠的就是下面这个窗口化流控。
**2026-07-27 更新**：找到逐行流控下的算法拐点后，容差已从 0.2mm **提前降到 0.1mm**，
`linemerge` 对齐奎享 `nearDst=0.3`。细节密度翻倍，实机串口 0 行阻塞。要再追奎享的
0.254mm 密度，只能上窗口化流控。

#### 动作 4：窗口化流控（大改，仍是最终正解）

**完整设计已独立成文：`docs/design/p2-windowed-flow-control.md`**（含窗口取值依据、
`WaitResponse` 计数障碍、换纸行排空、四阶段落地与回退阀）。本节只留摘要。

要点：
- Pipe 侧 EventGroup 单 bit **不能计数多个 ok**，必须换计数信号量——这是第一块硬骨头
- Job 侧需预解析成行列表（现状边扫边发，无 peek 能力）
- 窗口起步 **512 字节**（Telnet `_RXbuffer` = 1200，见设计文档 §3）；不照抄奎享的 100
  - 注：串口路径实测 `Bf` 第二数恒 128（findings/09），1200 只在 Telnet 客户端查询时出现
- 换纸行前必须把在途排空（换纸期禁发 G0–G3）
- 需改 `docs/protocol.md` §3 契约（②③ 共同契约，两侧同步评审）

> **收益边界（2026-07-28 实测）**：窗口化只作用于高往返链路。
> COM3 串口 A/B（183 行，窗口 1 vs 512）= 40.38s vs 40.42s，**无差异**——
> 串口往返 6ms，瓶颈是电机运动时间。**收益只在 WiFi Telnet 链路（20–40ms）出现**，
> 且必须在 Telnet 上验收，串口实测不能作为收益证据。

### P3：对齐细节（已被真实产物纠正，无需再做）

#### 动作 5：G0 → G1 空走 —— 已撤销

真实产物证明奎享空走就是 **G0**，我们原本用 G0 是对的。此前的"改 G1"结论来自误读校准测试图代码。

#### 动作 6：去掉 segment 的 F —— 已撤销

## 四、不做的（明确排除）

1. **不改 Grbl 固件**：M3/M5 宏留着，只是上位机不再发 M3/M5。Grbl 源码不动 → 不用跑 fz 门禁。
2. **不碰换纸**：上位机/下位机换纸不兼容（用户已确认），不研究。我们的换纸靠 M30 触发固件内置流程，与奎享的 ESP2/3 事件不同。
3. **不参数化 Z 值**：第一版硬编码 Z=5.0/Z=0.0/F10000，验证通再说。
4. **不改流控**：P2 暂缓，逐行等 ok + linesimplify 当前够用。
5. **不改 error 中止策略**：奎享**同样中止**（原「它容忍」是错的，见 §五）。差别只在它有
   `error:120` 静默白名单和 `error:9` 弹框解锁交互；我们无人值守不能弹框，故不引入交互，
   保持一律中止。
6. **下载文件不含 `G92 Z0`**：校验器继续拒绝；但完整会话必须由 S3 受控旁路发送。
7. **不改 `$1/$3`**：保持奎享本机 `$1=25`、`$3=7`，以等待 100ms + `G92 Z0` 处理回弹后的计数漂移。

## 六、对齐后的预期下载文件（完整示例，逐字对齐真实产物）

完整会话先由 S3 执行 fresh `Idle` + 100ms + 旁路 `G92 Z0`，再发送下列文件：

```gcode
G21                              # document_start
G90
F8000
G1G90 Z0.0F10000                 # 缓存兼容的幂等抬笔（第 1 次）
G1G90 Z0.0F10000                 # 第 2 次（不建立基准）
G0 X75.000Y222.000F8000          # segment_first：空走到起点
G1G90 Z5.0F10000                 # 落笔
G1 X84.412Y224.519F8000          # segment：画线
G1 X93.824Y225.488F8000
G1G90 Z0.0F10000                 # line_end：抬笔
G0 X100.000Y180.000F8000         # 下一段空走
G1G90 Z5.0F10000                 # 落笔
...
G1G90 Z0.0F10000                 # document_end：收尾抬笔（无 G0 X0 Y0）
```

与奎享缓存中的唯一 G-code 内容逐字同构，唯一有意偏差是收尾不含 `G90G0 X0Y0`
（换纸触发，§5 禁止）。9 个缓存文件内容相同，不能扩大为 9 份独立证据。
