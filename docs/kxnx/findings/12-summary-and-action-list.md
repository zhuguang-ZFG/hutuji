## 二、hutuji 现状 vs 奎享 对照总表

| 维度 | 奎享（逆向） | hutuji 现状 | 差距 | 改动优先级 |
|------|--------------|-------------|------|-----------|
| **笔控指令** | `G1 G90 Z5/Z0 F3000` | `M3` / `M5` + `G4 P0.2` | 宏失效 | **P0 必改** |
| **Z 基准校准** | 首次笔控前 `G92 Z0` | 无 | 落笔失败根源 | **P0 必改** |
| **流控** | 窗口 100 字节，连续发 | 逐行等 ok | 卡顿根源 | P2（已被 linesimplify 缓解） |
| **行数密度** | （不控制，靠窗口吸收） | linesimplify 0.2mm | 已修 | ✓ 已对齐 |
| **空走指令** | `G1` + F2500 | `G0` + F2500 | G0 更快但奎享用 G1 | P3 可选 |
| **F 声明** | 开头一次 | 每行带 F | 冗余 | P3 可选 |
| **`error:NN`** | 记录不中断 | 放弃整幅 | 我们更严 | 不改（场景不同） |
| **暂停** | 软暂停（停灌） | `!` 硬暂停 | 我们更好 | 不改 |
| **中止** | `0x18` + 清 s | `!` → 8s → `0x18` | 我们有 grace | 不改 |
| **进度推送** | `?` 状态事件驱动 | 5s 定时 + 行计数 | 等价 | 不改 |
| **坐标系** | 每文件 `G92 ...Z0` | 手动归零 XY | 缺 Z 校准 | P0（同笔控） |
| **WiFi port** | 23 | 23 | ✓ | 一致 |
| **传输** | Java Socket + flush | lwip socket | 同构 | 不改 |
| **keepalive** | 应用层看门狗 | TCP keepalive 三参数 | 等价 | 不改 |
| **设备发现** | mDNS | 早期 mDNS 已去 | 我们更激进 | 不改 |

## 三、落地清单（按优先级）

### P0：让笔能落纸（当前阻塞项，必做）

#### 动作 1：`hutuji_gwrite.toml` 笔控改 G1Z

```toml
document_start = "G21\nG90\nG92 Z0\nF1500\n"
segment_first = "G1 X{x:.3f} Y{y:.3f} F2500\nG1 G90 Z5.000 F3000\n"
segment       = "G1 X{x:.3f} Y{y:.3f}\n"
line_end      = "G1 G90 Z0.000 F3000\n"
document_end  = "G1 G90 Z0.000 F3000\n"
```

- 落笔 Z=5（实测触纸），抬笔 Z=0
- `G92 Z0` 在 document_start 校准 Z 基准（对齐奎享首次笔控前校准）
- 去掉 `M3`/`M5`/`G4 P0.2`
- 证据：findings/01, 02, 03, 05, 07
- 风险：低（纯模板文本，不动代码）
- 验证：COM3 串口直发，看纸上线条

#### 动作 2：确认 `$1=255` 仍在生效

之前为防弹簧回弹设过 `$1=255`（电机永不失能）。笔控改 G1Z 后仍需要它。
检查 NVS 没被重置。

### P1：稳定性（出图跑通后做）

#### 动作 3：实机端到端验证

- 部署 toml 到 VPS
- 小智语音画一张（或 VPS 直调 hutuji_draw + S3 转发）
- 验收：纸上出现完整图案

### P2：性能（可选，当前已被 linesimplify 缓解）

#### 动作 4：窗口化流控（大改，暂缓）

若将来需要更高行密度（复杂图、写字）再考虑。改动 `hutuji_job.cc::StreamToGrbl`：
- 预解析 buffer 成行列表
- 维护 in_flight_bytes + 在途队列
- `Pipe::WaitResponse` 改成事件消费
- 需改 `docs/protocol.md` §7 契约 + fz 门禁 + 实机验证

### P3：对齐细节（可选）

#### 动作 5：G0 → G1 空走

奎享空走用 G1 + F2500。我们用 G0（rapid）。G1 更稳（限速防抖动），
但 G0 更快。**暂不改**，除非发现抬笔空走时刮纸。

#### 动作 6：去掉 segment 的 F

奎享只在开头声明 F1500，后续 G1 不带 F。我们每行带 F1500。冗余但无害。
**暂不改**，除非要严格对齐。

## 四、不做的（明确排除）

1. **不改 Grbl 固件**：M3/M5 宏留着，只是上位机不再发 M3/M5。Grbl 源码不动 → 不用跑 fz 门禁。
2. **不碰换纸**：上位机/下位机换纸不兼容（用户已确认），不研究。我们的换纸靠 M30 触发固件内置流程，与奎享的 ESP2/3 事件不同。
3. **不参数化 Z 值**：第一版硬编码 Z=5/Z=0/F3000，验证通再说。
4. **不改流控**：P2 暂缓，逐行等 ok + linesimplify 当前够用。
5. **不改 error 容忍策略**：我们严格中止更适合语音远程场景。

## 五、证据强度评级

| 结论 | 证据强度 | 依据 |
|------|----------|------|
| Stepper 走 G1Z 不用 M3/M5 | **强** | 字面量代码 + 跨固件一致（Grbl/Marlin） |
| G92 Z0 首次笔控前发 | **强** | `a.java:250-260` 明确 |
| 窗口 100 字节流控 | **强** | `b.java` 双队列 + `g()==100` |
| Z=5 触纸 | **实测** | COM3 串口验证 |
| M3 宏失效 | **实测** | `G0 Z5` 落笔 / `M3` 不落笔 |
| 奎享不卡顿 | **推断** | 基于窗口化原理，未对比抓包 |
| `error` 容忍 | **强** | `c.java` 只记录不中断 |
| port 23 | **强** | `a.java:141` 硬编码 |

## 六、对齐后的预期 G-code（完整示例）

```gcode
G21                              # document_start
G90
G92 Z0                           # ← hutuji 加的 Z 校准
F1500
G1 X75.000 Y222.000 F2500        # segment_first：空走到起点
G1 G90 Z5.000 F3000              # 落笔（Z=5 触纸）
G1 X84.412 Y224.519              # segment：画线（继承 F1500）
G1 X93.824 Y225.488
G1 G90 Z0.000 F3000              # line_end：抬笔
G1 X100.000 Y180.000 F2500       # 下一段空走
G1 G90 Z5.000 F3000              # 落笔
...
G1 G90 Z0.000 F3000              # document_end：收尾抬笔
```

这份 G-code 与奎享 Stepper 模式现役序列一致（除 `G92 Z0` 位置——奎享连接时发，我们每次出图发，更保守）。
