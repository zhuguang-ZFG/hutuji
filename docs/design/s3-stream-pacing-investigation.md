## 3. 根因分析（v2 修订后）

### 3.1 灌流饿爬主嫌疑：S3 自己在灌流期反复回落 LOW_POWER（日志实证）

灌流窗口内的省电翻转实录（同一日志）：
- `780783 PERFORMANCE` → `784363 LOW_POWER (MAX_MODEM)` → `784783 PERFORMANCE` →
  `789583 LOW_POWER` → …（784363/789583/794773/799973/803443/805153/810353/813893/815563/820763，
  **~5s 一次**），与 ok 空窗节拍（~350ms 批化叠加 5s 级断电窗）同量级。

机制：LOW_POWER=MAX_MODEM 期间 S3 自己的 WiFi 进 modem-sleep，**ok 的到达（下行）被 AP
缓存到醒点**，表现为成批延迟；72a693a 的门控只按 ~4s 节拍**重断言** PERFORMANCE，
没有「任务活跃期常持」语义——每次 LOW_POWER 窗长达数秒，灌流被反复掐断。

### 3.2 等播报段（34.5s）：标志清除路径待查

`WaitForAudioOutputIdle` 等 `kDeviceStateSpeaking` 清除，上限 30s（300×100ms 轮询）。
本日志中它被吃满。**待查项（实机/源码双路）**：
- 谁置位/清除 `kDeviceStateSpeaking`（Application 状态机）；742603 时刻是否仍在播
  「好的开始画」TTS（若播报实际 ~4s 而状态 28s 未清，则是状态机清除缺陷）；
- 739213 的 MQTT goodbye → 关音频通道 → LOW_POWER 翻转是否打断了 speaking 态的正常清除；
- 换锚考古已结案（2026-08-24）：speaking 锚随 72a693a 引入且已在板上
  （merge-base 实证）——**本 08-22 日志展示的是修复前行为，修复后是否治愈无 HIL 证据**；
  下次真机窗口必须实测该等待的真实时长。

## 4. 方案（实机窗口执行，按序）

### A. 播报等待白等排查（**最先**——疑似 bug，单段 34.5s）
- 按 §3.2 待查项定位 speaking 态清除链；下次 HIL 直接量等待真实时长（加首尾日志）。
- 若确认 goodbye 路径让状态滞留吃满 30s 上限：在 goodbye/通道关闭路径同步清除
  或让等待识别「通道已关即放行」。治愈后该段回到真实播报时长（秒级）。

### B. S3 灌流期禁止回落 LOW_POWER（灌流主攻；xiaozhi-esp32 仓，不碰 §9 面）
- 改动：任务/灌流活跃期持 PERFORMANCE 锁（RAII 挂在 Job 的 streaming 段，
  复用 72a693a 门控的现有入口，扩语义为「活跃期常持、空闲才允许回落」）。
- 验证：同一测试件灌流，日志判据——灌流窗口内 LOW_POWER 事件 = 0、
  send→ok 中位 <15ms、灌流总时长 <5s。
- 风险：插电工位功耗/温升微升；host 测试 + fz/门禁照旧。

### C. Grbl 关 WiFi 省电（次选；B 未达标再动）
- `esp_wifi_set_ps(WIFI_PS_NONE)`，落点 `src/WebUI/WifiConfig.cpp`——**超 §9 白名单**，
  须用户点名批准 + fz 门禁 + 烧录窗口。

### D. TLS 预热与复用（下载段，可与 A 同批）
- 播报等待期（无论等多久）**预热 TLS 连接**：握手 4.5s 藏进等待期，下载零握手；
  预览/正式两次下载复用同一连接可再省一次。

### E. F 提速 A/B（运动段，独立于以上）
- 矩阵：同一张五角星，F8000（现役）vs F10000 vs F12000（$110/$111 上限内）；
  判据 = 纸面出墨连续性人工目视（对照 B-12 既有证据）+ 无断线/无拖尾。
- 注意：F 提速只缩 5.2s 的物理段——**A/B 先做**。
