## 3. 根因分析（v2 修订后）

### 3.1 灌流饿爬主嫌疑：S3 自己在灌流期反复回落 LOW_POWER（日志实证）

> **[superseded → §6]** 本节是结案前的主嫌疑推演，保留为决策记录。结案实证：主根因是
> 每 ok 一次的 LCD 屏刷阻塞灌流循环（§6），LOW_POWER 翻转只是叠加因素，已由 Grbl 关
> 省电一并消除。以本节为现行结论引用属于过期口径。

灌流窗口内的省电翻转实录（同一日志）：
- `780783 PERFORMANCE` → `784363 LOW_POWER (MAX_MODEM)` → `784783 PERFORMANCE` →
  `789583 LOW_POWER` → …（784363/789583/794773/799973/803443/805153/810353/813893/815563/820763，
  **~5s 一次**），与 ok 空窗节拍（~350ms 批化叠加 5s 级断电窗）同量级。

机制：LOW_POWER=MAX_MODEM 期间 S3 自己的 WiFi 进 modem-sleep，**ok 的到达（下行）被 AP
缓存到醒点**，表现为成批延迟；72a693a 的门控只按 ~4s 节拍**重断言** PERFORMANCE，
没有「任务活跃期常持」语义——每次 LOW_POWER 窗长达数秒，灌流被反复掐断。

### 3.2 等播报段（34.5s）：标志清除路径待查

`WaitForAudioOutputIdle` 等 `kDeviceStateSpeaking` 清除，上限 30s（300×100ms 轮询）。
本日志中它被吃满。**待查项（实机/源码双路）**：
- 谁置位/清除 `kDeviceStateSpeaking`（Application 状态机）；742603 时刻是否仍在播
  「好的开始画」TTS（若播报实际 ~4s 而状态 28s 未清，则是状态机清除缺陷）；
- 739213 的 MQTT goodbye → 关音频通道 → LOW_POWER 翻转是否打断了 speaking 态的正常清除；
- 换锚考古已结案（2026-08-24）：speaking 锚随 72a693a 引入且已在板上
  （merge-base 实证）——**本 08-22 日志展示的是修复前行为，修复后是否治愈无 HIL 证据**；
  下次真机窗口必须实测该等待的真实时长。

## 6. 结案（2026-08-24 实机窗口，插桩实证 + 修复 + 复测全齐）

**根因定案**（插桩 `[INSTR]` 三桶计时，证据 `results/local-only/2026-08-24/hil-instr-cat-com14-v4.log` 在本机）：
灌流循环每确认一行（ok）就 `UpdateDisplayProgress()` → LCD `SetStatus`（waveshare LVGL 屏刷
~60ms/次）——`hutuji_job.cc` 收分支逐 ok 调用。1151 行实测：总 74.0s = SendLine 5.0s +
TakeResponse 0.25s + **其它 68.8s（93%，≈60ms/行=屏刷）**。喂流 66ms/行 → 超过 `$1=25` 失能阈值
→ Z 电机失能 → 弹簧把笔弹回自然抬笔位 → 零距离 Z5 压不下笔 →「卡顿 + 不落笔」。
PC 直连无 S3 无屏刷 = 7.2ms/行（对照组）。

**修复（三件套）**：
1. 屏显 250ms 节流（`hutuji_job.cc` 收分支，屏显只反映节奏不收 ok 的账）；
2. 出图前缺纸预检**移除**（用户拍板「有纸无纸不用机器管」；GPIO34 是走纸到位传感器，
   静态 HIGH 是空闲常态，语义误用致误报；真缺纸证据只有自动换纸的 OUT_OF_PAPER）；
3. Grbl 侧 WiFi 关省电（`0e1b7ed`，STA 连上后 `WIFI_PS_NONE`；用户点名，§9 外授权例外）。

**修复后实测**（`hil-instr-cat-com14-v9.log` 在本机）：975 行 **17.2s**（17.6ms/行，
修复前 64ms/行）；另轮 910 行 23.3s。全链语音→画完→换纸正常，用户目视「有墨，画得好」，
不落笔消失。v8 全白判为单次喂纸物理事件（串口/PC 直连同文件均有墨）。

**残余观察项**：SendLine 12.8s/910 行（≈14ms/行写出成本）是新的主桶；PC 直连 7.2ms/行
为下界参照。是否再压（写出路径）按下一轮实测决定，不预设。

## 7. 复发与根治（2026-08-25，lichuang-dev 半墨）

**复发**：waveshare 修复三件套上线后，lichuang-dev 语音出图再现「半树无墨」。
抓包 `results/local-only/2026-08-25/tree-redraw-com14.log`（本机）：流完整
（540 发 540 收、零 error/ALARM、页尾全序列），固件全程报 Z=5.000，但纸面
树冠/框左缘微段区空白——物理笔位与固件 Z 开环分叉。落笔期空窗 10 次
230–640ms，与 TTS 播报（「写字机正在动笔…」）、`notify: 出图进度`、屏显同刻。

**根因**：§6 的 250ms 屏显节流只降频率，救不了单次锁等待。`UpdateDisplayProgress()`
内联 `display->SetStatus` 需拿 LVGL 显示锁；lichuang-dev 的 Grobot 全脸动画
（TTS 播报期嘴部帧连帧渲染）使主任务整帧持锁，灌流任务单次锁等待即达
230–640ms——远超微段区缓冲运动量（≈300–500ms），planner 排空 → `$1=25` 失能
→ 弹簧抬笔（设计行为，`PreparePenOrigin` 注释同款）→ 同段后续笔画无墨。
旁证：奎享/Inkscape PC 直连同机全墨（PC 发送端无此类阻塞）。

**根治**（xiaozhi `e623aec`）：`UpdateDisplayProgress()` 的 SetStatus 经
`Application::Schedule` 回主任务执行（仓规钦定模式），灌流任务只付互斥入队
成本；250ms 节流保留用于约束主任务队列流量。宿主 135/135；镜像
`build-jog-ws35/xiaozhi.bin` 3,017,280B SHA-256 `80e4ffe8…d7b7` 已刷 COM14。

**修复后实测**（`tree-redraw-fixed-com14.log` 在本机）：落笔期空窗 max 30ms、
>100ms **零次**（修复前 640ms/10 次），流 142/142 零错误，用户目视**全墨**。
`$1` 保持 25 未动（机器默认参数被 PC 主机证明充分，缺陷唯在 S3 发送端）。
附注：AI 生图链「画不像树」属生成质量另一议题（Quick Draw 缓存即为此设），
与本机制修复无关。
