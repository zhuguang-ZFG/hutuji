# 排障手册

> 按现象定位。契约定义见 `protocol.md`；联调阶段见 `bringup-sop.md`。本文不改写契约。

## 日志优先级

CH340 串口（最全）→ S3 `ESP_LOG` → Telnet 字节流 → 京东云 MCP / 桥接日志。

PC 观测一律走 CH340；Telnet 槽位 `MAX_TLNT_CLIENTS=1` 留给 S3。烧录 hash 通过只证明写入；必须再匹配启动 ELF。COM14 单独掉线先查端口重枚举与网络，不能直接定性整机掉电或固件崩溃。

## Waveshare COM14 / HIL 取证判读（2026-08-18）

- app-flash 的 `Hash of data verified` 只证明镜像写入，不能证明应用已启动。
- COM14 在触摸初始化后短暂消失，若稍后重枚举且启动横幅 ELF 与构建对齐、工具/Pipe/Idle 到达，就不能再写成“触摸后崩溃”。
- COM14 消失但 WiFi 仍通是 USB/串口层现象；只有 COM14、WiFi、屏幕等共同证据才能支持整机掉电判断。
- `_final_hil_capture.py` 摘要里的 `MISSING` 表示该动作未在采集窗内发生，不等于 PASS，也不单独证明固件失败。
- UI HIL 必须触摸真实控件；直接调用 `Job::Request*` 会绕过坐标映射、置灰门控与回调接线，不能替代。

## CH340 `COM3` 打开即 Windows error 31：已定位到 `SetCommState`（2026-07-31 实测）

**现象**：MK38 写字机板的 CH340（`VID_1A86&PID_7523`，`LOCATION=1-2`）在设备管理器里
`Status=OK / Problem=CM_PROB_NONE`（「设备运行正常」），`serial.tools.list_ports` 也照常枚举出 `COM3`，
但任何打开尝试都失败：

```
SerialException: Cannot configure port, something went wrong.
  Original message: PermissionError(13, '连到系统上的设备没有发挥作用。', None, 31)
```

**分层定位（决定性，别再重试三种库）**：用 ctypes 直打 Win32，逐个 IOCTL 分开看——

| 调用 | 结果 |
|------|------|
| `CreateFileW(\\.\COM3, RW, share=0)` | **成功**（拿到句柄）→ 不是被占用（占用会是 error 5） |
| `GetCommState` | 成功（能读回 DCB） |
| `GetCommTimeouts` / `ClearCommError` | 成功 |
| `SetCommState`（**原封不动回写 `GetCommState` 拿到的 DCB**） | **失败 err=31** |
| `SetCommState`（9600 8N1 / 115200 8N1） | 失败 err=31 |

即：驱动对象活着、能应答查询类 IOCTL，**只有把线路参数下发到芯片的那一步失败**。

**为什么这不是软件问题**：`SetCommState` 是打开串口的必经步骤——pyserial、esptool、PlatformIO、
`mode`、PuTTY 全都要调它，没有任何参数组合能绕过（连「不改参数、原样回写」都失败）。
所以**换库、换波特率、换脚本都是白费**；必须物理侧处理：重插 MK38 USB（优先）、换线/换口（供电或线序），
或**提权**后 `Disable-PnpDevice` + `Enable-PnpDevice` 重启该实例（本机 `elevated=False`，agent 侧做不到）。

**两个附带坑**：

1. `Get-PnpDevice` 报 `CM_PROB_NONE` **不能**当「串口可用」的判据——上面就是反例。
2. `SetCommState` 报失败后，下一次 `GetCommState` 会回读到**刚才那次失败尝试写入的波特率**
   （先读到 9600、试写 115200 失败、再读变成 115200）。别把这个当「配置已生效」。

另：`VID_1A86&PID_7522`（CH340K）另有两个 `CM_PROB_PHANTOM`（Code 45）的历史实例 `COM7`/`COM8`，
是拔掉后的残留登记项，与本故障无关；当前在线的 CH340K 是 `COM9`。

## 笔控 / 落笔出墨（2026-07-29 实测）

> **纸面是唯一判据。** `ok` 只表示该行已进 planner（`Protocol.cpp:147-158`），MPos 是开环步计数、无任何位置反馈（`Stepper.cpp:313-324`、`System.cpp:220-234`）——失步或笔尖未触纸时，日志照样报 `Z=5.000` 全程保持。**禁止用日志宣称“已落笔”。**

| 现象 | 可能原因 | 处置 |
|------|----------|------|
| 日志 Z=5.000 全程保持但纸上无墨 | 落笔进给被改慢；画线进给过快；笔压/机构 | 落笔恢复奎享原值 `F10000`；画线先降到 `F1500` 复测；纸面确认后再逐步回抬 |
| 落笔行发了但 Z 不动 | 逻辑 Z 已在目标值，零长度 block 被静默丢弃（`Planner.cpp:315-337`） | 落笔前确保 Z 基准为 0（会话旁路 `G92 Z0`），不要重复发同值 |
| 画一半墨断 / 笔被抬起 | 供料断粮 → segment buffer 空 → `st_go_idle()`；`$1=25` 后共享 EN 失能，弹簧抬笔 | 整笔期间保持窗口化连续供料（S3 `kWindow=512`）；不要逐行等 `ok` 慢灌。**注意**：生产参数下已实测不触发断粮（见下「本地实测」），别拿它当默认解释 |
| 手动单发 `G1 Z5` 能触纸，整文件却不出墨 | 手动只看到瞬时触纸（停止 25ms 后即失能回弹），不代表画线期间保持下压 | 用完整文件在纸上验，别把单条指令的“触纸”当结论 |

实测记录（S3 `3ca9d31` autodraw 镜像 + Grbl `8d13b5c`，同一文件内两条 50mm 直线）：

| 线 | 落笔 | 画线 | 纸面 |
|----|------|------|------|
| Y=177（先画） | `Z5.0F300` | `F1500` | **无墨** |
| Y=170（后画） | `Z5.0F10000` | `F1500` | **有墨，整条均匀** |

处置结论：当前 profile **保持奎享原值 `F10000`，不采用未经证明的 F1000/F300 降速方案**。

因果仍未区分，勿写成“F10000 必然解决落笔”：两条线同时混了落笔参数与先后顺序，不能排除“第一条在通墨”的顺序效应；纯奎享参数（落笔 `F10000` + 画线 **`F8000`**）在干净下载条件下从未测过；实机 `$112/$122` 未读到，若 `$112 < 10000` 则 `F10000` 会被钳到 `$112`。

### 2026-07-30 追加：手动 Telnet 全序列在纸面出墨（画线 `F800`）

用户手动逐条发的完整序列，实测落笔并划出线（**非 S3 自动路径，无归档日志**）：

```
G90
G92 Z0
G1 Z5.0 F10000     ← 落笔（奎享原值）
G91
G1 X10.0 F800      ← 画线：相对 10mm，约 750ms
G90
G1 Z0.0 F10000     ← 抬笔
```

它证实的是**结构**：`G92 Z0` 建 Z 基准 → `G1 Z5.0` 落笔 → 画线期间保持下压 → `G1 Z0.0` 抬笔，与 S3 `PreparePenOrigin`（fresh `Idle` + 100ms 后旁路 `G92 Z0`，fork `13057e8`）一致。

**别读过头**：

- 它**不为生产 profile 的画线 `F8000` 背书**。迄今全部纸面出墨点的画线进给都 ≤ `F1500`（`F1500`、`F800` 各一次），`F8000` 至今零纸面证据。
- 也不能把这条序列当下载文件模板：它用 `G91` 相对走，而生产下载文件全程 `G90`，校验器明确拒中途 `G91`（`docs/protocol.md:393`，回归 `test_mid_file_g91_is_rejected`）。
- 未证伪的机制假设：笔靠电机通电压住，`$1=25` 一停就失能、弹簧抬笔（见上表「画一半墨断」）。`F800` 走 10mm 约 750ms，远大于逐行 Telnet 往返 ~25ms，运动几乎不断；同一段在 `F8000` 下只需 ~75ms，行间空闲反倒占大头。若该假设成立，**根因是「运动有没有 >25ms 空隙」而不是进给数值本身**，那么 `F8000` + S3 窗口化连续供料（`kWindow=512`）同样可能出墨。

**长单段测试测不到生产工况（2026-07-30 补，测试设计缺陷）**：

奎享唯一真实产物的画线段长约 **0.044mm**（`G1 X-2.132Y1.169F8000` → `G1 X-2.174Y1.183F8000`，见 `docs/kxnx/findings/02-gcode-template.md:19-20`；946 行里 673 个 `G1`、全程 `F8000`，见同文件 `:29`）。`F8000`=133mm/s，一段只走 **~0.33ms**，真实图靠 planner look-ahead 把上千短段拼成连续运动。而手搓测试件一条线就是整段 50mm：`F8000` 下 375ms、`F800` 下 3.75s，**任何供料方式都不会断粮**。所以长单段出墨只证明「长段该进给能出墨」，对真实图零信息量——**测试文件必须含密集短段线**，否则下面第 2 步无效。

定量对照（机制推演，**已被本地实测限定适用范围**，见下一节）：

- planner 块深 `BLOCK_BUFFER_SIZE 250`（`Config.h:469`）够深，不是瓶颈。
- 在途量看 S3 窗口：`kWindow = 512` 字节 ≈ 21 行在飞（`hutuji_job.cc:74-75`），且**一行一个应答、禁止多行合并进同一 TCP 包**（`hutuji_job.cc:2506-2507`，商业固件会少应答、窗口计数永久漂移）。
- 失能门槛可解析求出：planner 空窗 = `RTT − 21 × 段长 ÷ 133.33mm/s`，空窗 > `$1`=25ms 才失能 → **只有段长 < (RTT−25) × 6.349 µm/ms 时才可能断粮**。RTT=40ms → 0.095mm；RTT=30ms → 0.032mm；RTT ≤ 25ms → 恒不失能。**注意这里代入的 20–40ms 已被实测证否**，实测值与重算后的门槛见下面「实测 `$110/$111/$112` 与链路 RTT」一节。
- 奎享为什么不受这条约束：它 0.044mm 段长下 21 段仅 6.93ms 在途。奎享支持三条通道——USB 串口（我们 COM3 实测往返 ~6ms）、WiFi TCP（port 23，与 hutuji 同构）、**蓝牙 SPP**（商业上位机无线主路径，`PAPER_AUTO_CHANGE_ON_BT_CONNECT` 量产验证，RTT 未知）。下方 6ms 是串口实测基线；同一份文件搬到 WiFi 40ms+ 往返就必失能——**奎享 `simplePaths=0.02mm` 不可照搬到 Telnet 路径**，hutuji 的 `linesimplify 0.05mm` 反倒是 WiFi 路径的必要保护。
- 交叉印证：`hutuji_pipe.cc:507-508` 关 Nagle 的注释已独立记过同一物理机制（Z5 执行后 `$1` 到点失能、下一条 XY 因等 ACK 滞留 → 轨迹在走但笔已回弹）。

### 本地实测：当前生产管线产不出会断粮的段长（2026-07-30）

直接调真管线（`from hutuji_mcp.gcode_gen import svg_to_gcode`）出产物，按 `G0` 切笔画统计段长，并算「任意连续 21 段的最小运动时间和」。脚本 `results/.tmp/measure_seglen.py`（不入库）：

| 探针 | 产物 | 段数 / 笔画 | 段长 min / p25 / median / p75 / max (mm) | 最坏连续 21 段 |
|------|------|-------------|------------------------------------------|----------------|
| 常规（R40 圆 + R3 圆 + 三次贝塞尔 + 波浪） | `lines=282 bytes=6619 pen_lifts=7` | 264 / 4 | 0.348 / 1.105 / 2.001 / 3.900 / 13.281 | **92.3ms** |
| 高曲率最坏（R0.5–3mm 小圆阵 + 0.5mm 密集波浪） | `lines=252 bytes=5843 pen_lifts=12` | 219 / 9 | 0.118 / 0.313 / 0.426 / 0.706 / 1.227 | **72.5ms** |

两者在 RTT=20/25/30/40ms 下全部安全（空窗为负）。高曲率的 min 0.118mm 正落回 `mcp-server/hutuji_mcp/gcode_gen.py` 记的原始离散步长 0.12mm——说明高曲率处 `linesimplify` 留不住，但连续 21 段是混合分布，对 40ms 往返仍有 2.9 倍余量。

> **本节结论已于 2026-07-30 被实测 RTT 推翻，勿再照抄**。上面那句「20/25/30/40ms 下全部安全」的前提（RTT ≤ 40ms）是估计值，实测应用层 RTT 下界 ~77ms、p50 ~117–134ms，代入同一公式后**两个探针都会断粮**。原结论「断粮不是候选根因」**撤回**，改判见下一节。段长实测表本身有效，保留。

### 实测 `$110/$111/$112` 与链路 RTT：旁路 RTT 触发压力测试，Telnet 自动路径实测证伪断粮（2026-07-30）

上一节的判别性第 1 步已做完，结论与预期相反。

**进给未被钳（这条如预期）**：ws:81 旁路读 `$$` 拿到 46 条设置，`$110=12000.000`、`$111=12000.000`、`$112=10000.000`、`$120/$121=3000`、`$122=8000`、`$1=25`、`$3=7`、`$130=210`、`$131=297`、`$132=200`。与奎享本机（`docs/kxnx/findings/02-gcode-template.md:46`）**完全一致**：`F8000` 远在 XY 上限 12000 之内，`F10000` 正好等于 `$112` 上限、不被钳。所以 133.33mm/s 这个分母站得住，上面全部时间账的算术无需重算，**但代入的 RTT 错了**。

**RTT 实测（这条推翻原结论）**：设备 `192.168.1.13` 在线，`[ESP420]` 自证 `Sleep mode: Modem`、`Signal: 98%`、`Phy Mode: 11n`、`Channel: 1`、`CPU 240MHz`、`Free memory: 50.61 KB`。三条独立通道量出的往返：

| 通道 | n | min | p25 | p50 | p90 | max | 备注 |
|------|---|-----|-----|-----|-----|-----|------|
| ICMP `ping` | 2 | 115 | — | — | — | 304 | 平均 209ms |
| HTTP keep-alive 背靠背（gap=0） | 30 | 89.2 | 109.7 | **133.8** | 245.6 | 735.3 | `[ESP800]` |
| HTTP keep-alive gap=20ms | 20 | **84.1** | 89.8 | **116.6** | 186.6 | 441.8 | 最接近逐行供料节奏 |
| HTTP keep-alive gap=500ms | 12 | 96.3 | 104.2 | 117.2 | 161.8 | 203.4 | — |
| HTTP 每次新连接 gap=0.4s | 12 | 97.9 | 103.5 | 110.8 | 139.6 | 192.2 | — |
| ws:81 `?`→状态报告 | 20 | 77.2 | — | 556.3 | 713.9 | 718.6 | p50 偏高见下 |

判读要点，别越读：

- **`Signal: 98%` 排除链路质量**，`Sleep mode: Modem` 是首要嫌疑：ESP32 STA 默认 modem-sleep 按 DTIM 周期醒（1 beacon = 102.4ms，与实测 p50 117–134ms 同量级，且解释了 `gap=500ms` 与背靠背几乎同延迟——延迟来自被动等 beacon，不是拥塞）。
- **ws:81 的 p50 556ms 不可当供料 RTT**：`?` 的响应经 `_socket_server->loop()`（`WebServer.cpp:1561`）在主循环里被动泵出，叠了固件轮询周期。该行的价值只有 min=77.2ms——它给出**应用层往返的实测下界**。
- **HTTP 短连接 RTT ≠ Telnet 长连接 RTT**，这几行都不是 Telnet 实测值。但三条通道的 min 一致落在 77–98ms，**下界具有跨通道一致性**，而下界已经足以翻结论。

代入 `段长 < (RTT−25) × 6.349 µm/ms` 重算门槛，并与实测段长对照：

| 代入 RTT | 断粮门槛段长 | 常规探针（最坏 21 段 92.3ms）空窗 | 高曲率（72.5ms）空窗 |
|----------|--------------|-----------------------------------|----------------------|
| 40ms（旧估计） | 0.095mm | −52.3ms 安全 | −32.5ms 安全 |
| **80ms（实测下界）** | **0.349mm** | −12.3ms 安全 | +7.5ms（<25，仍安全） |
| **117ms（实测 p50）** | **0.584mm** | **+24.7ms（临界）** | **+44.5ms 失能** |
| **134ms（背靠背 p50）** | **0.692mm** | **+41.7ms 失能** | **+61.5ms 失能** |
| 209ms（ICMP 均值） | 1.168mm | +116.7ms 失能 | +136.5ms 失能 |

**B-12 改判**：上述重算只证明 HTTP/ws 旁路 RTT 足以设计压力测试，**不能直接扩大成 S3 Telnet 长连接的现实断粮结论**。2026-07-30 上机跑同一测试件后，Y=185 `0.2mm × 250`、Y=192 `0.6mm × 83`、Y=199 `1.2mm × 41` 三档密段与五条长单段全部纸面连续出墨；按旁路 RTT 下界 77ms 推导，本应最先断的 Y=185 实际不断。因此 B-10 的「断粮重新成为现实候选根因」撤回。合理解释是：HTTP/ws 旁路 RTT 不代表 S3 的 Telnet 长连接逐行供料；Grbl planner 预读、TCP 缓冲和 S3 窗口化共同吸收了短暂 modem-sleep 卡顿。`WiFi.setSleep(false)` 仍可作为消除卡顿的体验优化，但不再是防断粮必要修复；放大 `kWindow` 暂无证据支持。

局限：Telnet 长连接（S3 实际走的通道）RTT 仍未直接实测，见下条「PC 侧无法并连 Telnet」；`WiFi.setSleep(false)` 的收益仍是推演，未实测。本轮只证明在 `13057e8`/`0x2ce890` 自动路径和当前网络条件下，压力阶梯没有触发断粮。

## PowerShell 5.1 读无 BOM UTF-8 脚本 = 伪语法错（2026-08-07 实测）

**现象**：写一个带中文注释的 `.ps1` 去发串口序列，`powershell.exe -File` 报一串莫名解析错——
`意外的标记「}」`、`「<」运算符保留供将来使用`、`Try 语句缺少 Catch 或 Finally 块`，
报错行号还指向语法完全正确的行。空跑护栏因此在发送前就退出（这次是好事：零运动指令）。

**根因**：本机 `powershell.exe` 是 **5.1**，`[Console]::OutputEncoding` / 默认代码页为 **gb2312**。
PS 5.1 读 `.ps1` 时**没有 BOM 就按当前 ANSI 代码页解**，不会猜 UTF-8。于是文件里 569 个
非 ASCII 字节（中文注释）被按 GBK 拆开，某些字节对被解成伪引号/伪括号，把后续 token 全带偏——
报错行号是错位后的位置，跟真正的语法无关。

**判据与处置**：

```powershell
$b = [IO.File]::ReadAllBytes($p)
$hasBom = ($b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF)   # 必须 True
[System.Management.Automation.Language.Parser]::ParseFile($p, [ref]$null, [ref]$errs)  # 校验再跑
```

- 写 `.ps1` 一律用 **UTF-8 with BOM**(`utf-8-sig`)；本仓约定注释用中文，所以这条**每次都会踩**。
- 或退化方案：脚本内**只用 ASCII**，中文说明留在配套 `.md` 里。
- 跑之前先 `ParseFile` 静态校验，别让「伪语法错」浪费一轮硬件窗口。
- 同源提醒：`bash` 工具里写 PowerShell 时，反引号会先被 shell 吃掉(本轮 `-split` 的 `` `n `` 就是这么丢的，切行切在字母 n 上)。需要反引号就写文件再 `-File` 执行,不要内联。

## `[ESP901]` 有纸的字面量是 `Paper=OK`，不是 `Paper=Yes`（2026-08-07 源码核实）

`PaperSystem.cpp:358-359` 的格式串是 `"Paper=%s ..."` + 三元 `paper_ok ? "OK" : "No"`,
故有纸状态输出 **`Paper=OK`**。启动日志里另有 `GPIO34(HIGH=NoP LOW=HavP)` 与 `M704` 的
`NoP/HavP` 写法,那是**引脚电平注释**,不是 `[ESP901]` 的字段值——按 `NoP/HavP` 或 `Paper=Yes`
写匹配的护栏会 100% 误判。

但**「有纸」的护栏不能只匹配 `Paper=OK`**（2026-08-07 COM10 两次实测）：`M30` 自动换纸**成功**
的终态是 **`Paper=No` + `PanelHold=On`**——第 6 步快送直到 `sensor=lost`（尾缘越过传感器）、
第 7 步反向回找到 `sensor=found`（精确定位尾缘）、第 8 步再向前 350 步对位，尾缘**又一次**越过
传感器。`Paper=OK` 只在纸恰好压住 GPIO34 时成立（例如人工把纸直接放到台面传感器下）。
可靠判据是 **`PanelHold=On` 且 `Changing=Off`**:`paper_panel_low_hold_active` 仅由
`paper_enter_panel_low_hold()`（`PaperSystem.cpp:443-463`）置位,而它**只在
`paper_auto_change` 成功收尾处被调用一次**(`:1028`),任何 `paper_disable_drivers()`
(`:392`)都会清零——含**Grbl 复位**,因为它是 RAM 里的 `volatile bool`。

**现象**：脚本 A 发 `M30` 送纸成功（`PanelHold=On`）并 `Close()`；紧接着脚本 B 打开同一 COM
口，读到的第一段是**开机横幅**（`Grbl_ESP32 Ver 1.3a ...`），`MPos` 从 `10.000,0.000,0.000`
归零，`PanelHold` 变 `Off`——纸虽然物理上还在台面，**电机夹持已随复位释放**。

**已证事实**:`.NET SerialPort` 显式 `$sp.DtrEnable = $true` / `$sp.RtsEnable = $true` 后,
`Close()` 紧接着出现开机横幅、`MPos` 归零且 `PanelHold` 清零,说明该打开/关闭周期确实触发了
复位。早先同轮对照中,显式设 `$false` 后 `OPEN-EMITTED: (nothing)`,曾被解释为“打开不复位”。

**2026-08-07 20:52 复测收紧**:COM10 从“设备无响应”恢复后,`diag.ps1` 仍在 `Open()` 前显式
设置 DTR/RTS 为 `$false`;打开后 400ms 的 `OPEN-EMITTED` 为空,但发送只读 `?` 并再等 600ms
后收到完整开机横幅。随后不再打开串口,Grbl `192.168.1.13` 与 S3 `192.168.1.12` 均恢复为
连续 3/3 ping。该单次样本不能区分是本次 Open 触发、设备此前已在重启,还是横幅延迟到达,
但足以否定“`OPEN-EMITTED` 为空即可证明未复位”。因此**不得再把 DTR/RTS=false 当成无复位保证**。

**规避**:
- 仍应在 `Open()` 前显式设置 DTR/RTS 为 `$false`,但只把它当减小复位风险,不当保证。
- 把任何 Open/Close 周期都视为潜在复位点;打开后先等启动窗口结束并重新确认授权、fresh `Idle`
  与纸张夹持状态,再执行有状态操作。
- **有状态的多步操作必须写在同一脚本内、全程只 Open 一次**——送纸与出图之间不得 Close/reopen。
- 判断「是否刚复位」不能只看打开后首个缓冲;须覆盖启动窗口持续采集,并核对开机横幅、`MPos`
  是否意外归零、`PanelHold` 是否清零。

**恢复后受控复测**：COM10 使用 WCH `3.9.2024.9` 驱动，父设备不是 Root Hub，而是
`USB\VID_058F&PID_6254` 通用 Hub；同一 Hub 还挂视频适配器与 USB 网卡。`DTR/RTS=false`
连续做 5 轮 Open/Close，只发送 `?` 与 `[ESP901]`：5/5 打开和状态应答成功、0 次启动横幅、
0 次端点失效。Close 后 40 次 ping 有 7 次零散丢包，但没有连续掉线后恢复形状，不能据此判复位。
Windows 当前电源方案的「USB 选择性暂停」原为 AC/DC `1/1`，已改为 `0/0`；切换后保持同一
COM10 句柄在线，PnP 仍为 `CM_PROB_NONE`。

**已知未解**：本轮较早的 14 行出图全部 `ok`、笔已抬起之后，COM10 端点确曾卡死——枚举仍在、
PnP `CM_PROB_NONE`、`Open()` 报「设备没有响应」。恢复原因和复现条件仍未定，5 轮空闲复测不能
覆盖电机负载。下一轮应先把 CH340 移到主板直连端口，再做「直连/当前 Hub × 空闲/出图」A/B；
卡死时用管理员 `pnputil /restart-device "<instance-id>"` 取代反复 Open，不先回滚当前驱动。
不要把 Hub 或选择性暂停写成已证根因。

## `G91` 手动片段会把 X 一路顶到机械死点（2026-08-07 用户实测指出）

**现象**：反复跑「画 10mm 线」的手动片段，X 轴一直往右走，最终顶到极限位。

**根因**：那段片段是

```
G90
G92 Z0
G1 Z5.0 F10000
G91              ← 切相对模式
G1 X10.0 F800    ← 相对 +10mm，**从不返回**
G90
G1 Z0.0 F10000
```

`G91` 后的 `G1 X10.0` 是相对进给，每跑一次 X 就 +10mm 且不回退：`MPos.X` 实测已从
`0` 走到 `10.000`。反复跑就是 10 → 20 → 30 … → 撞 `$130=210` 的机械死点。

**为什么固件不拦**：本机 `custom_3axis_hr4988.h` 里 `X/Y/Z_LIMIT_PIN` **三个全部注释掉**，
`DEFAULT_SOFT_LIMIT_ENABLE 0`（`$20=0`）、`DEFAULT_HOMING_ENABLE 0`（`$22=0`）。
**Grbl 完全不知道任何轴的物理边界**，相对模式下更没有「绝对目标」可比——
它会老老实实把电机往死点上顶。软限位即使打开也需要先归零才有意义，而本机无限位开关。

**生产链不受此威胁（已实测复核，勿混为一谈）**：

- 下载文件被 `validate_gcode()` 的指令白名单锁死，只放 `G0/G1/G2/G3/G21/G90`。
  实测 `G91` 独立行、`g91` 小写、`G1G91` 同行混排、`G92 X0` 全部按
  「第 N 行含 G91（生产文件允许 …）」拒绝——注意**必须用带合法尾行的样本复测**，
  否则文件末尾契约会先触发，掩盖白名单是否真的拦住了 `G91`。
- S3 旁路指令：绝对 Z 运动 `G1G90 Z…`、`G92 Z0`（只动 Z 不动 XY）、`M5`、`M30`，以及 2026-08-14 起的页尾归位行 `G1G90 X0Y0F8000`（XY 运动、G1 不触发换纸）、
  `$I`、`$X`、`?`、`!`、`0x18`；授权探针 `BuildLicenseProbeLine(x)` 用当前 MPos 构造
  **零位移** `G1 G53`。全仓检索 `main/boards/lichuang-dev/` 无任何 `G91`。

**处置**：手动脚本一律遵守三条——

1. **动前算目标绝对位置并自行拒绝越界**，不靠固件兜底（`$20=0` 时没有兜底）。
2. 用了 `G91` 就必须**抬笔后相对返回同等距离**，使净位移为 0；收尾复核 `MPos.X`
   是否回到起始值，不回到就报警（可能丢步或返回段被拦）。
3. 中途失败退出前注意**模态可能停在 `G91`**，需手动补发 `G90`，否则下一条裸轴字
   会被按相对模式执行。

`results/.tmp/manual_line_draw_com10.ps1` 已按此重写为幂等版（越界前置拒绝 +
抬笔返回 + 净位移复核）。**该脚本尚未在恢复后的 COM10 上跑过**，只做过 PowerShell
AST `ParseFile` 静态校验（PARSE OK）。

## BLE 只读诊断辅助面与外部资料取证（阶段 A 已实现）

BLE 排障必须先确认边界：S3 BLE 阶段 A 已提供 6 字节公开粗粒度状态广播，阶段 B 才提供需认证的 22 字节 GATT 只读诊断和阶段 C 的 RSSI 近距提示；Grbl 写字字机侧经典蓝牙 SPP 是另一器件的既有链路。正式板间数据仍只走 WiFi Telnet :23，任何 BLE 写命令、G-code、运动/换纸/job 控制或 UWB/AoA/Apple Precision Finding 表述都属于设计越界。

阶段 A 已有 host/构建/COM14 启用态广播与回滚证据，但仍未完成 §1.4.6 关闭/开启 BLE 同场共存量化、完整功耗/温升和阶段 B/C。后续启用任一 BLE 阶段，必须按 `docs/protocol.md` §1.4.6 做关闭/开启 BLE 同场对照：至少 3 次、每次 30 分钟、20 个确定性 job 和 10 次受控断连。记录 S3 启动身份、WiFi/Telnet RTT p95/p99、窗口应答错配、job 终态、断连恢复、最低堆内存、功耗、温升、看门狗/复位原因和原始日志。任一硬门槛失败先关闭 BLE 收敛，不得改 Telnet 流控或超时迁就辅助面。RSSI 只用于手机/PC 端相对近距提示；5 样本中位数、5s 窗口、3s 无样本为 `unknown`，不能据单点 RSSI 推导距离或方向。
