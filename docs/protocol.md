# hutuji 板间协议与 G-code 契约 v0.2

本文是 ②（S3 固件补丁）与 ③（MCP 服务）的共同契约。改动需两侧同步评审。
v0.2：按两仓代码勘察结论修订（Grbl_Esp32 `c19a382`、xiaozhi-esp32 `38bc4f4`）。

## 1. 物理层

| 项 | 约定 |
|----|------|
| 介质 | **USB 线**：写字机 USB-A（板载 **CH340**，即 Grbl UART0=GPIO1/3）→ 实战派 USB-C（S3 原生 USB，**Host 模式**） |
| 驱动 | S3 侧 esp-iot-solution `espressif/usb_host_ch34x_vcp`（需加入 `main/idf_component.yml`），枚举 CH340 后为透明字节流 |
| 参数 | **115200 8N1**（Grbl_Esp32 `Config.h` 默认，CH340 透传，不改） |
| 流向 | S3 → Grbl：G-code 行；Grbl → S3：`ok` / `error:NN` / `[MSG:]` / 状态报告 |
| 供电 | 写字机自供电；S3 可否从 VBUS 取电待实测 |

**重要认知**：这条 CH340 链路同时是写字机的**诊断日志口**——`grbl_msg_sendf(CLIENT_SERIAL,…)` 全部输出（含 `[PaperAuto-*]` 换纸进度）都在此流上，S3 解析器必须按 §2 容忍全部输出类型。

**备用链路**（Host 受阻时回退）：TTL 飞线，实战派排针空闲 UART ↔ 写字机 CH340 输出侧，3.3V、TX/RX 交叉 + GND。需拆机，非首选。

**S3 侧 USB-C 走线待确认**：实战派 C 口疑似两路（CH343→UART0 下载口 + 原生 USB→GPIO19/20）。已确认代码侧 GPIO19/20 空闲（控制台走 UART0，无 USB_SERIAL_JTAG）。验证法见 §1.1。

### 1.1 实战派 C 口走线验证（②开工第一步）

1. C 口插 PC，设备管理器出现 **CH343 串口** → 下载/调试路存在。
2. 烧 esp-idf `tinyusb_cdcacm` 示例：PC 上**新增** USB 串口 → 原生 USB 通到 C 口，Host 方案零改线。
3. 若无：查原理图跳线；再退至排针引 GPIO19/20 D+/D-。结果补记于此。

## 2. 就绪检测与会话重建

- **开机 banner**（全部 `\r\n` 结尾）：ESP32 ROM 日志 → `[MSG:Grbl_ESP32 Ver 1.3a …]` → `[MSG:Using machine:Custom 3-Axis HR4988]` → `[MSG:Paper system: M701 M711 M712 M713]` → `[MSG:[Paper] …]` → `[MSG:[ESP32ID] ChipID …]` → `[MSG:[License] Authorized …]`（**必须出现**，见 §6）→ 最后 `\r\nGrbl 1.3a ['$' for help]\r\n`。
- **以 `Grbl 1.3a ['$' for help]` 作为"固件就绪"标志**；此前不得发送任何 G-code 行。
- **会话重建**：写字机可能因电源欠压随时复位（面板电机大电流），表现为断流后重放 banner。解析器在任意状态下看到就绪标志都要复位状态机、放弃当前任务并上报。
- **解析器必须容忍**（异步混入字节流，均非应答）：`[MSG:…]`（含 `[MSG:[PaperAuto-N] …]`、`[MSG:[PaperStatus] N]` 双层括号）、`?` 触发的 `<Idle|MPos:…|FS:…>`、`ALARM:n`、`[BT-EOL …]` 等裸 `[…]` 行。

## 3. 流控（Grbl 行协议）

- **逐行发送，收到 `ok\r\n` 才发下一行**；`error:NN\r\n`（数字格式）按 §7 处理。**无 character-counting**，禁止预发抢跑（client_buffer 溢出会丢字节）。
- **单行 ≤ 255 字符**（`LINE_BUFFER_SIZE 256`），超长回 `error:11`。MCP 生成端折行负责。
- **换纸阻塞期**（数十秒）：该行的 `ok`/`error:90` 在**整个换纸完成后**才返回——这类行（M30/M721/[ESP910]）等 ok 超时 ≥ 60s，期间用 `[MSG:[PaperAuto-N]…]` 进度行做 UI 反馈；且此期间**禁发任何 G0–G3**（会被吞并回 `error:8`，见 §7）。
- 实时命令（`!` 暂停、`~` 恢复、`?` 状态、`0x18` 软复位）单字节立即生效，可混在流中；`?` 的应答只回给发送口。
- **`0x18` 特例**：换纸开始后 8s 窗口内被忽略（打印 `Host reset (0x18) ignored`）；窗口后才中止换纸。`abort` 实现须注意（§4）。
- 空行、注释（`;` 与 `()`）由 S3 转发前剔除。

## 4. 任务协议（S3 设备侧 MCP 工具）

**并发约束（勘察结论）**：xiaozhi 的 MCP 工具回调在**主任务同步执行**——禁止在回调里跑长任务（会卡死音频上行泵与状态机，云端还会等超时）。因此全部工具**异步化**：

| 工具 | 参数 | 行为 |
|------|------|------|
| `hutuji.draw` | `url` | 回调仅校验参数+幂等检查 → 立即返回 `"started"`；独立任务执行：HTTP 流式下载（`Board::GetNetwork()->CreateHttp()` + `Read()` 循环，模板见 `ota.cc:299-367`）→ 校验（§5）→ 按行切分 → ch34x 写 → 等 ok |
| `hutuji.status` | — | 同步快速执行：透传 `?` + `[ESP901]`（纸/电机/PanelHold 状态）+ `M704`（GPIO34 纸传感器），汇总返回 |
| `hutuji.abort` | — | 发 `!` 暂停 → 延迟 ≥8s 后发 `0x18`（避开换纸忽略窗）；终止下载转发任务 |

- 任务完成/失败经 `Application::SendMcpMessage` **设备侧主动推送**给云端；同步查询走 `hutuji.status`。
- 状态机：`idle → downloading → streaming → (paper_change) → done | error`；`abort → idle`；任意状态收到 banner 重放 → `error`（固件复位）。
- 同一时刻只允许一个任务。
- 代码挂点：`lichuang-dev` 板级 `InitializeTools()`（参照 `press_to_talk_mcp_tool.cc` 独立工具类模式）；**板级行为不进核心模块**（xiaozhi 仓 AGENTS.md 规则）。

## 5. G-code 文件契约（MCP 服务产出）

- **自包含**：文件头 `G21`（毫米）、`G90`（绝对）、`F` 进给。
- **避开隐式换纸触发点**（勘察发现，现役固件会自动换纸，不想要时必须规避）：
  - 软复位后**第一条** `G0 X0 Y0 Z0`（首页触发）
  - `G28` / `G30`，以及执行后工件坐标 XY≈0 的 `G0`（回原点触发，含 `G0 X0 Y0` 收尾！）
  - **结论：分页节奏必须显式控制**——页尾用 `M30`（自动走完整换纸流程），队首可用 `M721`；收尾**不要**用 `G0 X0 Y0`（会误触发换纸），抬笔后停当前位置即可。
- **抬/落笔**：机头用 `USE_M3_M5_AS_PEN_UP_DOWN`（M3=落笔 / M5=抬笔，Z 步进非伺服，与纸路电机共用 GPIO25 DAC）。现役样例 `两页示例_插入换页.gcode` 用 `Z30` 落 / `Z0` 抬 + `G4 P0.2` 稳定，机头默认 `PEN_UP/DOWN_Z_MM=0/5`——**以 ② 实测锁定**（先查 `$102` Z steps/mm，偏小会落笔不够）。
- **坐标范围**：`$130/$131 = 200/200mm`（`custom_3axis_hr4988.h`），**软限位 `$20=0` 关闭**——越界不报错只撞机，MCP 生成端必须自行限幅（建议留边距 ≤190×190）。
- **换纸失败语义**：`error:90`（M30/换纸失败）；`[MSG:[PaperStatus] N]`：0=成功，2=进纸超时，3=回找未定位，4=卡纸，5=缺纸。N≠0 → 暂停任务 + 云端提示用户（加纸/清卡纸），不自动重试。
- **大小上限**：单文件 ≤ 512KB（边下边转，②实测修订）。

## 6. 授权前置（勘察发现）

- 未授权芯片上电后 **G0–G3 全部回 `error:110`**。就绪检测时必须确认 banner 含 `[License] Authorized`。
- 未授权 → 走人工 SOP（按 ChipID 算授权码，`M800 P<码>` 写 NVS），**S3 不自动授权**。
- 注意：烧录不覆盖 NVS，授权与 `$` 设置持久；改机头默认需 `$RST=$`（联调 SOP 记录，非 S3 职责）。

## 7. 错误处理

| 情况 | 含义 | S3 行为 |
|------|------|---------|
| `error:8` | 换纸进行中，运动行被推迟 | **不算失败**：暂停发送，等换纸行 ok / `[PaperStatus]` 后继续 |
| `error:11` | 行超 255 字符 | 任务 error，上报（MCP 生成端 bug） |
| `error:90` | 换纸失败 | 任务 error，按 `[PaperStatus]` 码提示用户 |
| `error:110` | 未授权 | 停止全部发送，提示走授权 SOP |
| 其他 `error:NN` | 语法/参数错 | 停止，记录行号，任务 error 上报 |
| `ALARM:n` | 报警 | 停止；`$X`/`$RST` 解锁走人工 SOP，不自动解锁 |
| banner 重放 | 固件复位（欠压等） | 状态机复位，任务 error，上报 |
| 下载失败/超时 | — | 不发任何字节，任务 error |
| 60s 无 `ok`（换纸行 90s） | 链路异常 | 发 `?` 探活一次，仍无则任务 error |

## 8. 明确不做

- 不用蓝牙、不用 WiFi 走正式数据链路（理由见 README 决策记录 #2）。
- S3 不做 G-code 生成/编辑/预览，只做校验与转发（哑管道原则）。
- 不改动 Grbl 侧任何代码（现役商业固件；勘察确认其串口/换纸/授权行为已满足全部对接需求）。
- S3 不自动授权、不自动 `$X` 解锁、不在换纸 8s 窗口内发 `0x18`。
